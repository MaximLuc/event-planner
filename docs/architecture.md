# Архитектура бэкенда

[Главная](../README.md) · [Разработка API](../apps/api/README.md)

## Основные процессы

```text
Swagger / будущий React-клиент
    |
    v
API (main.ts)
    |-- PostgreSQL: пользователи, сессии, события, заявки, приглашения
    |-- Redis: кэш и счётчики ограничений запросов
    `-- BullMQ / Redis
            |
            v
        Worker (worker.ts)
            |-- PostgreSQL: актуальные данные приглашения
            `-- SMTP -> Mailpit
```

API и worker запускаются отдельно из одного проекта и Docker-образа. Worker не принимает HTTP-запросы: он обрабатывает очередь писем и может перезапускаться независимо от API. Это не независимые микросервисы — у них общая схема БД.

## Ключевые решения

- **Авторизация.** Access token возвращается в JSON, refresh token — в HttpOnly-cookie. В БД хранится хеш refresh token; при обновлении токен ротируется. Logout отзывает refresh-сессии, но выданный access token действует до истечения срока.
- **Конкурентное редактирование.** Изменения черновика и публикация проверяют `expectedVersion` и увеличивают `version`. Устаревшая версия приводит к `409 Conflict`.
- **Вместимость.** Подсчёт подтверждённых участников и занятие места выполняются в `Serializable`-транзакции с ограниченными повторами при конфликтах. Уникальные пары в БД защищают от повторных регистраций и приглашений.
- **Кэш.** Публичные данные сохраняются в Redis на 60 секунд. Ключ списка включает фильтры, пагинацию и ревизию; изменение ревизии переключает запросы на новые страницы, старые удаляются по TTL.
- **Ограничение запросов.** Redis хранит общие счётчики для нескольких экземпляров API. Ключи кэша, throttling и очереди разделены префиксами.
- **Уведомления.** API сохраняет приглашение и ставит задачу с его ID в BullMQ. Worker перечитывает данные, пропускает неактуальные приглашения и отправляет письмо. Для ошибок предусмотрены три попытки с растущей задержкой.

## Данные и доступ

Пять основных моделей: `User`, `Session`, `Event`, `EventRegistration`, `EventInvitation`. Связи и ограничения описаны в [Prisma schema](../apps/api/prisma/schema.prisma).

Новое событие — `DRAFT / PRIVATE / INVITE_ONLY`. Видимость и политика участия независимы: публичное мероприятие может принимать участников только по приглашениям.

В витрину попадают опубликованные будущие события с видимостью `PUBLIC`. `UNLISTED` доступны по прямой публичной ссылке после публикации, `PRIVATE` через публичный API недоступны. Публичные ответы не содержат email организатора и служебных полей.

## Окружение и проверки

Docker Compose запускает инфраструктуру, применяет миграции и затем поднимает API и worker. E2E-тесты используют отдельные PostgreSQL, Redis и Mailpit через Testcontainers, не рабочую БД.

GitHub Actions проверяет линтер, типы, сборку, e2e и сборку Docker-образа. Публикация образа и деплой пока не настроены.

## Ограничения

- Compose — локальное окружение, не production-конфигурация.
- Кэш допускает задержку обновления данных до TTL.
- Запись приглашения и постановка задачи не атомарны; при сбоях возможны пропущенные уведомления или повторные письма. Outbox и устранение дублей пока не реализованы.
